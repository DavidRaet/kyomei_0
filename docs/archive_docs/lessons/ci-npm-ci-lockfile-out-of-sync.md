# CI Post-Mortem: `npm ci` failing in GitHub Actions, passing locally

**Date:** 2026-07-18  
**Component:** `.github/workflows/ci_cd_workflow.yml` (`test-and-lint` job, `Install dependencies` step)  
**Error:** `npm error npm ci can only install packages when your package.json and package-lock.json ... are in sync.` followed by `npm error Missing: @emnapi/core@1.11.2 from lock file` (and `@emnapi/runtime`)

---

## What happened

Every push failed CI at the `npm ci` step, on both matrix legs (`18.x`, `20.x`). Running `npm ci` locally — even in a totally clean, empty temp directory with just `package.json` and `package-lock.json` copied in — succeeded without any error. The lockfile looked fine from a Windows machine.

An attempt was made to fix it by running `npm run install` and pushing the resulting `package-lock.json` diff. The pipeline still failed afterward, with the exact same error.

---

## Root cause: two separate problems stacked on top of each other

### Problem 1 — `npm run install` is not `npm install`

This project's `package.json` has no `"install"` script. `npm run install` doesn't fall back to running a real install — it just fails:

```
npm error Missing script: "install"
```

So the "fix" never actually regenerated anything. Whatever produced the committed lockfile diff wasn't a genuine full `npm install`.

### Problem 2 — the lockfile only had platform-specific entries, not a hoisted one

Vite 8 uses `rolldown`, which ships per-OS/CPU native binding packages (`@rolldown/binding-linux-x64-gnu`, `@rolldown/binding-win32-x64-msvc`, `@rolldown/binding-wasm32-wasi`, etc.) as `optionalDependencies`. The wasm fallback variant depends on `@emnapi/core`/`@emnapi/runtime`.

In the broken lockfile, `@emnapi/core`/`@emnapi/runtime` only existed **nested** under `@rolldown/binding-wasm32-wasi`'s own `node_modules` entry — there was no top-level (hoisted) `node_modules/@emnapi/core` entry. `npm ci`'s validation of "does the lockfile fully account for the tree package.json implies" is stricter on Linux runners than it apparently was in the resolution that produced this lockfile, and the missing hoisted entry only surfaced as an error under the platform where it was actually needed. On Windows, a different optional binding is relevant, so the gap never got exercised — which is exactly why local reproduction kept saying everything was fine.

The fix was to delete `node_modules` **and** `package-lock.json`, then run a real `npm install` from scratch. The regenerated lockfile hoisted `@emnapi/core`/`@emnapi/runtime` to the top level, and `rolldown` itself picked up a newer patch release (`1.1.4` → `1.1.5`) in the process.

---

## Lessons

**1. A same-OS local repro that passes does not prove the lockfile is actually complete.**  
Optional, platform-gated dependencies (native bindings, wasm fallbacks) mean a lockfile can be valid-looking on Windows and broken on Linux, or vice versa. If CI fails and a local `npm ci` in a clean directory succeeds, suspect a platform-specific branch of the dependency tree before assuming the lockfile is fine.

**2. Don't hand-patch or partially regenerate `package-lock.json`.**  
A "fix" that only tweaks a couple of `"peer"` flags or a couple of lines is a signal that the lockfile wasn't actually regenerated by npm from scratch — it was nudged. When `npm ci` says the lockfile is out of sync, the reliable fix is: delete `node_modules` and `package-lock.json`, run `npm install` fresh, and let npm resolve the whole tree again.

**3. Double check the exact command you're running.**  
`npm run install` and `npm install` are not the same thing. Without an `"install"` script defined, the former silently does nothing useful — no error loud enough to be obvious unless you read the actual output.

**4. When you can't repro locally, read the actual CI logs instead of guessing from the UI.**  
`gh run view --log-failed` against the failing run gave the exact missing-package-and-version detail (`@emnapi/core@1.11.2`) that made the root cause traceable in the lockfile. The GitHub Actions UI summary/annotations view didn't show that detail.

**5. Keep the CI matrix aligned with what your dependencies actually support.**  
`eslint@10`, `vite@8`, and `@vitejs/plugin-react@6` all require Node `>=20.19`. Testing against Node 18 (EOL) was already producing `EBADENGINE` warnings and would likely have caused a second, unrelated failure right after this one was fixed. Matrix versions should track the `engines` requirements of your actual dependency tree, not just "whatever LTS versions existed when the workflow was written."
